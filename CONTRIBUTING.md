# Contributing

Thank you for helping improve Domoticz Solar Forecast. Contributions of bug fixes, tests, documentation, and carefully scoped enhancements are welcome.

## Before starting

1. Search existing issues and pull requests to avoid duplicate work.
2. For a significant change, open an issue first to discuss the approach.
3. Keep changes focused. Avoid combining unrelated refactors and behavior changes.
4. Preserve upstream attribution and comply with the GPL-3.0 license.

## Development setup

The current plugin uses the Python standard library only. Python 3 and a checkout of the repository are sufficient for the offline tests.

```sh
python3 -m unittest discover -s tests -v
python3 -m compileall -q plugin.py solarforecast
```

If you add dependencies, explain why they are necessary, document installation/runtime impact, and update `requirements.txt` and the tests accordingly.

## Design principles

- Keep `plugin.py` as a thin Domoticz callback/metadata entry point.
- Put configuration, API access, forecast calculations, device management, and lifecycle orchestration in their respective modules under `solarforecast/`.
- Keep calculation functions deterministic and testable without a running Domoticz instance.
- Keep provider-specific API parsing inside the provider/API layer.
- Never log API keys, complete credential-bearing URLs, or sensitive location data unnecessarily.
- Use local calendar dates consistently and explicitly test midnight and date transitions.
- Do not silently present unavailable forecasts as real zero-production forecasts.
- Preserve existing Domoticz unit numbers unless a migration is documented and justified.
- Avoid introducing network access into unit tests; use representative fixture payloads.

## Pull request checklist

- [ ] The change solves one clearly described problem.
- [ ] Tests cover normal behavior and relevant edge cases.
- [ ] `python3 -m unittest discover -s tests -v` passes.
- [ ] `python3 -m compileall -q plugin.py solarforecast` passes.
- [ ] User-facing behavior/configuration is documented.
- [ ] No secrets, personal data, generated bytecode, or local configuration are included.
- [ ] License and attribution requirements are respected.
- [ ] Release/version changes are intentional and reflected in the changelog.

## Commit and pull request guidance

Use descriptive commit messages, for example `fix: cap forecast at local midnight` or `docs: clarify API key configuration`. Explain the motivation, behavior change, testing performed, and any compatibility implications in the pull request. Include log excerpts only after removing tokens, IP addresses, account identifiers, and other private information.

By submitting a contribution, you confirm that you have the right to submit it under the project's GPL-3.0 license.
